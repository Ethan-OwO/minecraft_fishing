# minecraft_fishing

Minecraft（Java 版）自動釣魚腳本：偵測右下角的**聲音字幕**「浮標濺水」（英文 `Fishing Bobber splashes`），出現時自動收竿、重新拋竿。

- 不讀記憶體、不改遊戲、不攔截封包，只做「看螢幕 + 按右鍵」
- 跟語言無關：你自己截一次字幕當模板，中文、英文、任何語系都能用
- 純 Python：`mss`（截圖）＋ `OpenCV`（比對）＋ `pynput`（滑鼠、熱鍵）

---

## 快速開始

### 1. 安裝（Python 3.10+，以 Windows 為主要目標）

```bash
pip install -r requirements.txt
```

### 2. 遊戲設定

- **選項 → 協助工具設定 → 顯示字幕：開啟**（「音樂與音效」裡也有同一個開關）
- 建議用**視窗化或無邊框全螢幕**。獨佔全螢幕下，部分系統截圖會是全黑
- 校正之後**不要改 GUI 縮放、解析度、視窗大小**，改了要重新校正
- 不要按 F1，它會連字幕一起隱藏

### 3. 校正（只需做一次）

```bash
python mc_fishing.py calibrate
```

1. 進遊戲拋竿，等右下角出現「浮標濺水」那行字幕時按 **F6** 擷取畫面
2. 第一個視窗：把右下角字幕會出現的範圍**框大一點**（字幕會往上堆疊，框寬也會變）
3. 第二個視窗（已放大）：**只框那一行文字**，不要框到左右的方向箭頭 `<` `>`

結束時會印出自我檢查的分數。模板存在 `calibration/template.png`，設定存在 `config.json`。

### 4. 測試（只偵測、不點擊）

```bash
python mc_fishing.py test
```

手動釣幾次魚，咬鉤時應該會看到 `★ 偵測到新的濺水字幕`，而且 `score` 接近 1、`brightness` 接近 255。

### 5. 開始掛機

```bash
python mc_fishing.py run
```

| 按鍵 | 功能 |
|---|---|
| F6 | 開始 / 暫停 |
| F7 | 結束 |

開始前手上要拿著釣竿，而且**浮標沒有拋出**。加上 `--debug` 的話，每次判定咬鉤都會把截圖存到 `debug/`，可以用來檢查誤判。

## 運作原理

### 1. 為什麼看字幕，而不是看浮標或聽聲音？

魚咬鉤的那一刻，`FishingHook` 會播放 `entity.fishing_bobber.splash` 音效。開啟字幕後，客戶端的 `SubtitleOverlay` 會把每個音效事件畫成右下角的一行字。換句話說，**字幕就是「音效事件」的視覺化版本，天生是一個乾淨、離散的訊號。**

| 方案 | 問題 |
|---|---|
| 偵測浮標下沉 | 浮標只有幾個像素，位置隨視角改變，還會受光線、水面、粒子、天氣干擾 |
| 錄系統音訊 | 要做頻譜比對，會被背景音樂、雨聲、其他生物的聲音干擾 |
| 寫 mod / 讀封包 | 已經不是外部腳本，大多數伺服器也明確禁止 |
| **字幕** | **位置固定（右下角）、字型固定、對比高（白字黑底）→ 非常適合模板比對** |

### 2. 模板比對與 NCC（`detector.py`）

把模板 `T`（w×h）放在搜尋區域 `I` 的每一個位置 `(x, y)`，計算正規化互相關（`cv2.TM_CCOEFF_NORMED`）：

```
              Σ T'(i,j) · I'(x+i, y+j)
NCC(x,y) = ─────────────────────────────────     T' = T − mean(T)
            sqrt( Σ T'² · Σ I'(x+i, y+j)² )       I' = 視窗 − mean(視窗)
```

它其實就是兩個「去平均後的向量」之間夾角的 cos 值，所以有幾個好性質：

- **對亮度、對比不敏感**：若 `I = a·T + b`（a > 0），NCC 恆為 1。字幕淡出就是 `a` 變小，因此分數幾乎不變。
- **對位置不敏感**：滑動視窗會掃過整個區域。字幕因為堆疊或框寬改變而移動，也一樣找得到。
- **和語言無關**：比對的是像素形狀，不是文字內容。

至於效能：直接計算的複雜度是 O(W·H·w·h)。OpenCV 對較大的模板改用 DFT 算相關（卷積定理），每個視窗的平均值和變異數則用積分影像以 O(1) 取得。實際上搜尋區域只有幾百像素見方，每幀只要幾毫秒。

### 3. 分段取最小值：從「平均吻合」變成「每段都吻合」

整張模板的 NCC 本質上是「所有像素的平均相關」。`Fishing Bobber splashes` 和 `Fishing Bobber retrieved`（收竿時一定會出現的字幕）共用前綴，光靠前綴就能拿到高分。

所以我們把模板**直切成 3 段，每段各自算 NCC，在同一個位置取最低分**：

```
S(x, y) = min_k NCC_k(x + x0_k, y)       # 第 k 段的分數圖往右平移 x0_k 才能對齊
```

用測試中的合成字幕實測：

| 方法 | 真正匹配的最低分 | 其他字幕的最高分 | 差距 |
|---|---|---|---|
| 整張 NCC | 0.984 | 0.815（`retrieved`） | 0.17 |
| **分段 min（3 段）** | **0.983** | **0.477** | **0.51** |

真正匹配的分數幾乎沒變，誤判的分數卻大幅下降，門檻 0.85 兩邊都有足夠的安全距離。這個做法就是用 AND 取代平均。

### 4. 新鮮度：把文字亮度當成時鐘

NCC 對淡出不敏感是優點，但也代表它**分不出這行字幕是剛出現的，還是幾秒前的殘影**。我們需要第二個訊號。

原版 `SubtitleOverlay` 的繪製方式：

- 文字灰階 = `lerp(255 → 75, 經過時間 / (3000 ms × 通知時間倍率))`
- **文字是不透明的**，只有背景框是半透明（約 80% 黑色）

所以文字像素的灰階值**完全不受背後遊戲畫面影響，而且隨時間線性下降**。它本身就是一個計時器。倍率為 1 時：

```
亮度 ≈ 255 − 60 × 經過秒數       → 門檻 200 ≈ 字幕出現後 0.92 秒內
```

做法上，用 Otsu 法把模板分成文字與非文字（自動避開陰影與背景），在比對位置取文字像素的**中位數**。用中位數而不是平均，是因為就算對位偏了 1px、少數像素落在背景上，結果也不會被拉偏。

**寬限期的時間計算**：咬鉤後 → 收竿 → 等 `recast_delay` 0.6 秒 → 拋竿 → 再等 `cast_grace` 1.5 秒才開始判斷。這時上一條字幕已經存在約 2.1 秒，亮度 ≈ 255 − 60×2.1 = 129，低於 200，所以不會被誤認成新的咬鉤。如果你把「通知時間」調到 2 倍以上，請相應加大 `cast_grace`。

### 5. 狀態機與開迴路控制（`state_machine.py`）

```
PAUSED ──F6──► CAST_PENDING ──(recast_delay 到)──► WAITING
                    ▲              右鍵：拋竿          │
                    │                                  │ 新鮮的濺水字幕 → 右鍵：收竿
                    └──────────────────────────────────┤ 超過 max_wait  → 右鍵：收竿
                                                       │ 連續逾時 2 次  → RESYNC（只按一下）
```

右鍵在 Minecraft 裡是**切換**：浮標在手上時按是拋竿，在水裡時按是收竿。腳本看不到浮標，只能靠「自己按了幾次」來推算狀態，這叫**開迴路控制（open-loop）**。一旦不同步（例如你在開始前先拋了竿），正常的「收＋拋」兩下就會變成「拋＋收」，浮標永遠在手上，永遠釣不到。

**RESYNC** 是一個最小的回饋機制：連續逾時，代表「信念很可能和實際不同步」，這時只按**一下**（奇數次）來翻轉奇偶性。就算判斷錯了，下一輪連續逾時也會再翻回來，最差只是浪費幾分鐘，不會整晚白掛。`tests/test_state_machine.py::test_recovers_after_desync` 用一個極簡的世界模型驗證了這一點：沒有 RESYNC 時一條魚都釣不到，有 RESYNC 時兩次逾時後就恢復正常。

狀態機刻意寫成**純函式風格**：只吃 `(時間, 有沒有咬鉤)`，只吐出 `Action`，完全不碰 I/O。所以所有邊界情況都能用假的時間做單元測試，主迴圈只負責執行它吐出來的 Action。

### 6. 其他工程細節

- **`time.monotonic()` 而不是 `time.time()`**：系統時間可能被 NTP 校時往回調，單調時鐘不會，計時才不會亂掉。
- **熱鍵回呼只把指令丟進 `queue`**：pynput 的回呼跑在另一條執行緒，而狀態機不是 thread-safe 的。另外，Windows 的低階鍵盤 hook 如果回呼太慢（超過 `LowLevelHooksTimeout`），系統會默默把 hook 移除。
- **DPI awareness**：Windows 開 125%/150% 縮放時，沒有宣告 DPI awareness 的程式拿到的座標是經過虛擬化的，截圖範圍會偏掉。
- **前景視窗檢查（安全機制）**：模擬的右鍵會送到「目前的前景視窗」。在 Windows Terminal 裡，右鍵等於貼上，所以只要前景不是標題含 `Minecraft` 的視窗，就絕對不點。
- **中文路徑**：`cv2.imread/imwrite` 在 Windows 上不支援非 ASCII 路徑，改用 `np.fromfile + cv2.imdecode`。
- **延遲載入 `mss` / `pynput`**：沒有螢幕的環境也能執行 `--help` 和測試。

## 參數（`config.json`）

| 參數 | 預設 | 說明 |
|---|---|---|
| `match_threshold` | 0.85 | 形狀比對門檻（分段 NCC 最小值） |
| `match_segments` | 3 | 模板切幾段；1 = 傳統整張 NCC |
| `fresh_brightness` | 200 | 文字亮度 ≥ 此值才算新字幕。資源包改過字色時要調低 |
| `cast_grace` | 1.5 | 拋竿後幾秒內不判斷咬鉤 |
| `recast_delay` | 0.6 | 收竿後隔多久再拋（Minecraft 右鍵有 4 tick 冷卻） |
| `max_wait` | 60 | 超過幾秒沒咬鉤就收竿重拋 |
| `resync_after_timeouts` | 2 | 連續逾時幾次就 RESYNC；0 = 停用 |
| `poll_interval` | 0.03 | 偵測間隔（秒） |
| `click_hold` | 0.05 | 右鍵按住多久 |
| `toggle_key` / `quit_key` | f6 / f7 | 熱鍵 |
| `window_title_keyword` | Minecraft | 前景視窗標題要包含的字串；`""` = 不檢查 |

## 測試

```bash
pip install pytest
python -m pytest
```

因為無法在 CI 裡開 Minecraft，`tests/synth.py` 會合成模仿 `SubtitleOverlay` 的畫面：整數倍 GUI 縮放、80% 黑底框、不透明點陣字、1/4 亮度陰影、多行堆疊、文字置中、淡出。測試分成三層：

- `test_detector.py`：偵測器本身。涵蓋新舊字幕、堆疊、亮背景、相似字幕誤判、無效模板
- `test_state_machine.py`：狀態機。涵蓋寬限期、逾時、暫停恢復、不同步後的自我修復模擬
- `test_run_loop.py`：用假的 `mss` / `pynput` 跑真正的主迴圈，驗證從熱鍵、比對到點擊的整條串接

## 疑難排解

| 症狀 | 可能原因 / 解法 |
|---|---|
| `test` 時咬鉤了但 score 很低 | 改過 GUI 縮放或解析度、搜尋區域框太小，或按了 F1 → 重新 `calibrate` |
| 截圖全黑 | 獨佔全螢幕 → 改成視窗化或無邊框 |
| 一直顯示「Minecraft 不在前景」 | 啟動器的視窗標題不含 `Minecraft` → 修改 `window_title_keyword` |
| 熱鍵或點擊沒反應 | Minecraft 以系統管理員身分執行 → 腳本也要用系統管理員身分執行（UIPI 限制） |
| 偶爾誤收竿 | 附近其他玩家的浮標也會產生同樣的字幕，這是這個方法的限制。用 `--debug` 查看 |
| macOS | 要給終端機「輔助使用」與「螢幕錄製」權限；不支援前景視窗檢查 |

## 注意

許多伺服器禁止巨集或自動釣魚，請只在單人遊戲或明確允許的伺服器上使用。
